- 2026-08-16 (critical bugfix + architecture fix): **Global shared ID system actually made real, project-wide — plus a live production bug found and fixed along the way.**

## Website Booking Flow (BlackDrivo.com) — key facts for any app touching shared booking data
- Website replicates PassApp's booking flow (region/country select → vehicle → book for myself/someone → review & payment) at `/booking` and `/booking/review`, writing to the same `bookings` table with `source: 'web'`.
- **Vehicle categories are per-country**: `vehicle_categories.country_code` must always be filtered on — a query without it silently mixes categories from every country. Website's `lib/booking/pricing.ts` `fetchPricedCategories()` does this; port the same filter if building this elsewhere.
- **Rental (multi-day) packages are NOT a separate `pricing_type`.** They live inside the SAME `category_pricing.hourly_variants` jsonb array as by-the-hour packages (`pricing_type = 'hourly'`), distinguished only by each variant's `duration_unit` field: unset/`'hours'` = hourly package, `'day'` = rental/day package. There is no `pricing_type = 'rental'` row anywhere in the schema — don't create one; filter variants by `duration_unit` instead.
- Not every category has hourly/rental data configured — package pickers must scan ALL of a country's `category_pricing` rows (not just the first category by sort order) and union the available durations, or they'll wrongly show "no packages available" for categories the admin hasn't configured yet. See `fetchAvailablePackages()` in website's `lib/booking/pricing.ts`.
- `category_pricing` can have a country-wide row (`city_code IS NULL`) and city-specific rows for the same category — prefer the country-wide row when no city context exists (order by `city_code` ascending nulls-first, take the first match).
- Website `bookings.source = 'web'`; Admin's Bookings.jsx/BookingDetail.jsx display this as "Website" (see `sourceLabel()`/inline ternaries) — any new source value needs a matching label added in both places.
- `bookings.booking_ref` (e.g. `BD-A1B2C3D4`) is never shown raw to end users anywhere — Admin's `utils/formatters.js` `displayId()` strips non-digit characters before display; website mirrors this as `lib/booking/money.ts` `displayBookingId()`. Any new UI showing a booking ID to a customer must do the same strip, not show the raw ref.
- New tables added for the website flow (additive only, no existing column/table touched): `client_banners`, `web_app_download`, `promo_codes` (public SELECT policy added for `is_active=true`), `booking_addons` (already had public SELECT). New columns added to existing tables: `bookings.someone_email`, `bookings.someone_title`. New RPC: `increment_promo_usage(p_code text)`.
- Website's Google Maps/Places calls are proxied through its own Next.js API routes (`/api/places/autocomplete`, `/details`, `/directions`, `/geocode`) using the same shared Google Maps API key — never call Google Places directly from the browser (CORS blocks it; this cost real debugging time once already).
- Card details entered on the website's payment step are NOT stored raw — only the last 4 digits are kept (rest masked) when writing to the shared `cards` table, unlike historically-lenient mobile-app patterns. Keep this masking if this flow is ever touched from another app.
- **Passenger profiles live in `passengers`, NOT `users`.** `bookings.passenger_id` foreign-keys to `passengers` (id = auth.users uid, matching PassApp's `SignupStep3.jsx` upsert shape: `name, email, phone, country_code, country, status, source`). An earlier version of the website's `/signup` and `/booking/review` wrote/read the `users` table instead — a different, effectively orphaned table — which silently left every website signup's name/phone blank and caused "Passenger details are missing" on checkout. Fixed in `app/signup/page.tsx`, `app/auth/callback/route.ts` (new Google OAuth callback), and `app/booking/review/page.tsx`'s profile fetch. Any new code touching passenger profiles must use `passengers`, never `users`.
- Website auth now has: `/login` (email/password + "Continue with Google" + "Forgot password?"), `/signup` (name, email, phone — region-formatted via `lib/booking/phone.ts` using the site's selected country — password, confirm password), `/auth/callback` (OAuth code exchange + ensures a `passengers` row exists), `/reset-password` (post-email-link password update). Google sign-in requires the Google provider to be enabled with a Client ID/Secret in the Supabase project's Auth settings — that's an external config step, not something set from code.
- **Driver/vendor payout must never blend a ride's `partner_rate`% with an add-on's own `driver_share`/`driver_share_type`.** Each add-on can have a DIFFERENT driver share than the base fare — computing `driver_payout` as one blanket % over (fare + add-ons) silently short-pays (or over-pays) the driver whenever they differ. The canonical itemized calculator is Admin's `src/utils/fareUtils.js` `calcBookingFare()` (base share, per-add-on share array, tip, driver total, BlackDrivo margin) — ported verbatim (same field names/logic) to CapApp as `src/lib/fareUtils.js`, used by `components/shared/FareBreakdown.jsx` and `screens/orders/RideHistoryDetail.jsx` so drivers/vendors see the same itemized split admins do, not a lump `driver_payout` number. PassApp's booking-creation code (`Payment.js`) and CapApp's three ride-completion recompute sites (`ActiveRideScreen.jsx`, `Home.jsx`, `RideActive.jsx`) must all split base-fare-share and addon-share separately when writing `driver_payout` — any new payout-writing code must do the same, not reuse a single `partnerRate * (fare+addons)` formula.
- **PassApp amount formatting**: whole numbers only, symbol-space-amount ("₨ 1,000" / "$ 1,000", no currency-specific branching, no decimals anywhere) via `src/lib/formatAmount.js` — NOT `Number.prototype.toLocaleString()`, which needs full ICU data Hermes doesn't ship by default and silently mis-groups digits on real devices (e.g. "12,45" instead of "1,245"). CapApp has an identical `src/lib/formatAmount.js` for the same reason. Any new amount display in either app must use this helper, never `.toFixed(2)` or bare `.toLocaleString()`.
- **`VehicleSelect.js` was deleted from PassApp** (was dead/orphaned — nothing navigated to it; `BookingFlow.js` is the real, currently-used vehicle-selection screen). If old docs/comments reference `VehicleSelect.js`, they're stale.
- **`drivers.user_id` must always equal `drivers.id` (both = auth.uid()).** `drivers` has a legacy `user_id` column separate from its primary key `id` — most RLS policies on `drivers` (own-row SELECT/UPDATE, e.g. `drivers_read_own`, `drivers can view own record`, `drivers_update_own`) check `user_id = auth.uid()`, NOT `id`. CapApp's driver signup (`src/screens/auth/SignupStep3.jsx`) was only setting `id` on the initial `drivers` upsert, leaving `user_id` NULL — the row still got created (an unconditional `with_check:true` INSERT policy allows it, and it's visible to admins via `is_admin()`), but the driver's OWN session could never see or update their own row afterward (RLS silently returns empty, no error) — "signed up fine, admin doesn't show them, then login shows no data." Fixed by always setting `user_id: uid` alongside `id: uid` on that upsert; backfilled all pre-existing `drivers` rows with `user_id = id` where it was null. Any future code that creates a `drivers` row must set both columns to the same auth uid.
- **`driver_vehicles` had no INSERT policy for a driver adding their own vehicle** — only `admin_vehicles_write` (admin) and `vendor_fleet_vehicles_insert` (driver must already be in a vendor's fleet) existed; an independently-signed-up driver adding a vehicle from CapApp's `VehicleForm.jsx` (`driver_id: profile.id`) hit a bare RLS rejection with no matching policy. Added `driver_own_vehicles_insert`/`driver_own_vehicles_update` (`driver_id = auth.uid()`), additive only. Same class of bug as the `drivers.user_id` issue — always check a table has an RLS policy for the actual writer (driver-self, not just admin/vendor) before assuming a missing row is a data bug rather than a policy gap.
- **CapApp's amount formatting funnels through one place**: `useCurrency()`'s `fmt`/`fmtFare` in `src/lib/CurrencyContext.jsx` now use CapApp's own `src/lib/formatAmount.js` (identical helper to PassApp's) instead of `toLocaleString()` — fixed centrally, so any screen already calling `fmtFare()`/`fmt()` picked up the "₨ 1,000" whole-number/space format for free. A few screens still had their own inline `.toFixed(2)` bypassing the shared formatter (`ActiveRideCart.jsx`) — those were switched to call the shared helper directly.
- **Hermes' missing-ICU unreliability isn't just numbers — it also breaks date formatting.** `toLocaleDateString(locale, {day,month})`/`toLocaleString('en-PK', ...)` can silently give month-first "Aug 22" instead of day-first "22 Aug" on real devices, same root cause as the amount-grouping bug. Fixed via a new shared `src/lib/dateFormat.js` (CapApp) — `fmtDayMonth()`/`fmtDayMonthYear()` use `Intl.DateTimeFormat.formatToParts()` to reliably pull numeric day/month/year (numeric Intl parts ARE reliable even without full locale data) and build the "22 Aug" string manually, never relying on a locale's word order or month-name spelling. Pass a `timeZone` arg only where the original code already forced one (e.g. Home.jsx's `fmtDateTime` forced Asia/Karachi); otherwise it uses device-local time to match prior behavior. Any new date display added to CapApp (or ported to PassApp/Admin) should use this pattern instead of raw `toLocaleDateString`/`toLocaleString`.
- **`calcBookingFare()`'s addon-share fallback double-counted add-ons whenever `driver_payout_pct` is 0/missing.** When `driverPct > 0` the function correctly recomputes the ride-fare share fresh from `driverSubtotal` (base fare only, addons excluded) and adds each add-on's own share separately — safe. But when `driverPct` is 0 (falls back to the raw stored `driver_payout` column), that stored value's semantics are ambiguous — CapApp/PassApp write it as an already-combined base+addon total in some paths (e.g. Hour/Day Rent's vendor_rent). Adding `addonBreakdown` shares on top of that fallback double-counted the add-on portion ("Fare already includes the add-on's %, then the add-on shows again at 100% on top"). Fixed in both Admin's `src/utils/fareUtils.js` and CapApp's ported `src/lib/fareUtils.js`: addon `driverAmt` is now only computed (non-zero) when `driverPct > 0`; when falling back to the raw stored total, addon rows show as 0 so nothing gets added twice.
- **Vendor Portal had the same `driver_payout` + full addon-price double-counting bug, independently reimplemented in 4 places.** `D:\BlackDrivoVendorPortal\src\pages\bookings\BookingDetail.jsx`'s "Payout Split" card and `Bookings.jsx` (stats/earnings `payoutSum()`, CSV `handleExport()`, and the table's Fare column) were all summing `driver_payout + tip_amount + SUM(addon.price)` — the raw full addon price, not the addon's driver SHARE — on top of a `driver_payout` that (after the PassApp/CapApp write-time fixes above) may already include that share. Fixed by porting the canonical calculator to a new `D:\BlackDrivoVendorPortal\src\utils\fareUtils.js` (identical logic to Admin's/CapApp's `calcBookingFare()`/`getAddonDriverAmount()`, with one addition: defensively handles `addon_details` arriving as an already-parsed array from Supabase's jsonb auto-parsing, not just a JSON string — worth back-porting to Admin/CapApp if that edge case is ever hit there) and using `calcBookingFare(booking).driverTotal`/`.driverRidePayout`/`.addonBreakdown` everywhere a payout figure is shown or summed. All 4 Vendor Portal `.select()` queries touching payout had to be widened to include `driver_payout_pct, fare_estimate, fare, fare_final, wait_charge` (previously only fetched `driver_payout, tip_amount, addon_details`) since the itemized calculator needs those fields to recompute the base-fare share.
- **Website fare-breakdown had 2 real bugs, found via audit, both fixed.** (1) `lib/booking/promo.ts`'s min-fare rejection message hardcoded a `$` prefix regardless of the selected country's currency — a PKR user saw "Minimum fare of $500" for what was actually Rs 500. Fixed by threading `symbol`/`currencyCode` into `applyPromoCode()` and using `formatMoney()` for the message (and the promo-applied success toast in `app/booking/page.tsx`). (2) `app/api/booking/create/route.ts`'s driver-payout `partner_rate` lookup always used the country-wide `category_pricing` row (ordered by `city_code` nulls-first, took row #1) even when the customer's fare was actually priced off a city-specific override row — `fetchPricedCategories()` (`lib/booking/pricing.ts`) does proper city-first matching via `matchesCity()` (pickup address text contains the city_code), but the payout lookup didn't mirror it, so a city with its own `partner_rate` would silently under/over-pay the driver on every web booking. Fixed by mirroring the same city-match-then-country-fallback selection in the create route. Any other place that reads `category_pricing` for a `partner_rate`/config value (not just the customer-facing price) must use the same city-first matching, not a bare "first row" pick.
- **Admin's customer receipt (`generateReceipt()` in BookingDetail.jsx) mislabeled the GRAND total as "Base Fare".** `booking.fare` is the grand total (base + addons + tax + tip − promo — same shape PassApp's `Payment.js` and the website's `create/route.ts` both write), but the receipt showed `booking.fare` on a row labeled "Base Fare" while ALSO listing each add-on on its own row below — so the add-on amount appeared twice (once baked into the mislabeled "base", once again on its own line), inflating what looked like the base price. This is distinct from the driver-payout double-counting bug fixed earlier — this one was a customer-facing display bug, not a payout calculation bug, and it affected every booking source (PassApp/CapApp/website), not just one. Fixed by using `calcBookingFare(booking).baseFare` (already isolated, addons/tax excluded) for the "Base Fare" row, added a Tax row, and fixed the Total to prefer `fare_final || fare || fare_estimate` (previously `fare_estimate` — base+addons only, tax-excluded — was wrongly preferred over the actual `fare` grand total as a fallback). The invoice PDF generator (`generateInvoicePDF`) elsewhere in the same file already did this correctly — only the plain-HTML receipt had the bug.
- **CRITICAL, platform-wide bug: `JSON.parse(booking.addon_details || '[]')` silently returned `[]` for EVERY booking, everywhere, because Supabase's JS client already auto-parses jsonb columns into a JS array — `JSON.parse()`-ing an array coerces it to a string first ("[object Object]", not valid JSON), throws, and every one of these sites caught the error and fell back to an empty array with no visible error anywhere.** Net effect: `addonTotal` computed as 0, so every addon's price stayed folded inside "Base Fare" (never split into its own line) and each addon's driver share was never added to `driverTotal`/`driverRidePayout` — this is what booking `BD-01186` (a website booking, reported 2026-08-22) showed: its Rs 5,000 "Agent Service" addon was invisible and its Rs 6,927.95 `fare_estimate` (base+addon combined) was shown as the full "Base Fare" instead of the correct Rs 1,927.95. VendorPortal's own `src/utils/fareUtils.js` had already been written correctly (`Array.isArray(booking.addon_details) ? booking.addon_details : JSON.parse(...)`) when it was ported earlier this session — that fix was NOT back-ported to the original Admin/CapApp/PassApp copies until now. Fixed in ALL of: Admin's `src/utils/fareUtils.js` (canonical `calcBookingFare()`) + `BookingDetail.jsx`'s own local `addons` parse + `DriverSettlement.jsx` (×2, stats/CSV aggregates) · CapApp's `src/lib/fareUtils.js` + `RideActive.jsx` + `ActiveRideScreen.jsx` + `Home.jsx` (all 3 driver-payout ride-completion recompute sites) · PassApp's `src/lib/fareUtils.js` + `FareBreakdown.jsx` + `RideHistoryDetailB2C.js` + `RideDetail.js`. **Any new code anywhere that reads `booking.addon_details`/`ride.addon_details` must check `Array.isArray(...)` first, never assume it's a JSON string** — this is now the standard pattern across all 5 repos.
- **Vendor Portal's Assign Driver modal under-matched drivers by vehicle category.** `BookingDetail.jsx`'s `matchingDrivers` only compared `driver_vehicles.vehicle_category_id` (uuid FK) against `booking.vehicle_category` — but a vehicle can have its `vehicle_class` text field set (e.g. "Premium") while `vehicle_category_id` is null (confirmed in DB: driver "Adil Raza"'s Honda City Aspire has `vehicle_class: "Premium"`, `vehicle_category_id: null` — added via a path other than VendorPortal's own `AddVehiclePage.jsx`, which sets both together). That driver silently never matched ANY category filter, so a vendor with 2 Premium drivers only saw 1 in the assign modal. Fixed by falling back to a `vehicle_class === categoryName` text match when `vehicle_category_id` is null/unmatched (`driver_vehicles` select widened to also fetch `vehicle_class`). This is the same underlying data-quality gap as the `is_active` default-false issue fixed in `FleetMap.jsx` — some vehicle-insert path elsewhere in the platform isn't setting `vehicle_category_id` even when it sets `vehicle_class`. Worth an eventual audit of every `driver_vehicles` INSERT (CapApp's own vehicle-add flow is the likely culprit, not yet checked) to make sure `vehicle_category_id` is always set alongside `vehicle_class`.
- **PassApp/CapApp premature-logout bug**: `autoRefreshToken: true` on the Supabase client alone does NOT reliably refresh the session in React Native — the JS timer driving the refresh loop gets suspended once the app is backgrounded (unlike a browser tab, which stays alive), so a user who leaves the app idle/backgrounded for a while came back to an expired access token with no refresh in flight, which read as "logged out after some time." Supabase's own React Native docs require wiring `AppState` manually. Fixed in both `PassApp/src/lib/supabase.js` and `CapApp/src/lib/supabase.js` — an `AppState.addEventListener('change', ...)` now calls `supabase.auth.startAutoRefresh()` when the app becomes active and `supabase.auth.stopAutoRefresh()` otherwise. Any new Supabase client created for a React Native app in this project must include this same wiring from the start — website (Next.js) doesn't need it (browser tab visibility already keeps the refresh timer alive).
